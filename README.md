# Heart to Heart Enrichment Center website (hearts25.com)

Static, five-language (en, es, ar, sw, fr) website for Heart to Heart Enrichment Center,
3095 W. 25th Street, Cleveland, OH 44113. It has no package dependencies. A Node script
generates 130 pages, Netlify hosts them, and Supabase plus Resend handle registrations,
inquiries, tour requests, analytics and email. Netlify Forms is **not** used and must stay disabled.

## Layout

| Path | Purpose |
| --- | --- |
| `build.mjs` | Generates every page into `dist/` and copies `public/` |
| `pages.json`, `locales.json`, `forms.json`, `page-translations.json`, `registration.json`, `p0.json`, `p0-safety.json`, `p1.json` | English content, translations, form copy, release content layers (`p1.json` is generated by `tools/gen-p1.py`) |
| `inquiry-form.mjs`, `netlify-tour-form.mjs` | Form markup. All forms, including the tour request, post to the `website-inquiry` Edge Function. (`netlify-tour-form.mjs` and the `data-netlify-tour` attribute are legacy names for the tour form's JS hook; they do not use Netlify Forms.) |
| `public/` | Copied as-is: `assets/site.css`, `assets/*.webp`, `assets/inquiry.js`, `assets/analytics.js`, `assets/language.js`, `_headers`, `robots.txt`, `llms.txt` |
| `netlify.toml` | Build command and publish directory |
| `supabase/migrations/` | Database schema (private `website_private` schema, service-role-only access) |
| `supabase/functions/website-inquiry/` | Edge Function: validates every form (enrollment, contact, registration, information, tour), stores it, returns a persisted reference, sends the family and staff emails, records the success analytics event |
| `supabase/functions/tour-request-mailer/` | Edge Function: internal mailer for tour requests. Called only by `website-inquiry` (shared-secret header); it is **not** a Netlify Forms webhook |
| `supabase/functions/site-event/` | Edge Function: first-party, cookie-less analytics counters |
| `tools/` | QA and one-time helper scripts (see below) |
| `.env.example` | Variable template (no values) |

## Build

Requires Node 22 or later and one environment variable:

```
H2H_PUBLIC_ANON_KEY=<Supabase anon (public) key> node build.mjs
```

`H2H_PUBLIC_ANON_KEY` is the project's **anon / publishable** key (JWT with `"role":"anon"`). It is public client configuration:
it is embedded in `assets/inquiry.js` and `assets/analytics.js` and is visible to every visitor. It is **not** a secret and must
never be the `service_role` key. Data access is protected by RLS and service-role-only SQL functions. Find it in the Supabase
dashboard under Project Settings -> API Keys. The source contains only the placeholder `__H2H_PUBLIC_ANON_KEY__`; the build fails
if the variable is missing.

- **Build command:** `node build.mjs`
- **Publish directory:** `dist`

Apart from that key, output is deterministic.

## Deploy the website (Netlify)

Netlify project: `heart-to-heart-enrichment` (site ID `2c0a0593-ea18-4f4f-88bc-dd30a5d39ac5`), domain `hearts25.com`.
Each deploy replaces the whole site. **Netlify Forms must stay disabled** (Site configuration -> Forms): the built HTML contains no
Netlify form markup and nothing may reintroduce it.

### Current production method: prebuilt deploy

The Netlify connector used for deploys cannot set environment variables (HTTP 403), so production is deployed as a prebuilt `dist/`:

```
H2H_PUBLIC_ANON_KEY=<anon key> tools/make-prebuilt-bundle.sh /tmp/h2h-deploy
```

This builds the site and writes `/tmp/h2h-deploy/` containing `dist/`, a no-op `build.mjs` and a `netlify.toml`
(`command = "node build.mjs"`, `publish = "dist"`). Upload that directory with the Netlify connector or CLI
(for example `npx netlify-cli deploy --prod --dir=/tmp/h2h-deploy/dist --site <site-id>`).

### Optional: enable Git-based deploys (owner action)

1. Netlify -> **heart-to-heart-enrichment** -> **Site configuration** -> **Environment variables** -> **Add a variable**.
2. Key `H2H_PUBLIC_ANON_KEY`; value = the Supabase **anon / publishable** key (Supabase -> Project Settings -> API Keys). Never paste the service_role key.
3. Scopes: **Builds** (all deploy contexts). Save.
4. Connect this repository under Site configuration -> Build & deploy -> Continuous deployment (production branch `main`), then **Deploys -> Trigger deploy -> Clear cache and deploy site**.

Until this is done, do not deploy straight from Git: the build would fail on the missing key.

## Deploy the backend (Supabase)

Project ref: `zebeclcvrdmisnxkwode` (Heart2Heart website, us-east-2). Production migration history matches `supabase/migrations/` file names and versions.

1. Migrations (in order): `supabase db push`, or run the files in `supabase/migrations/` on a fresh project. Do not re-apply them to production. Current set:
   `website_inquiry_intake`, `child_registration_intake`, `lock_down_rls_auto_enable`, `p0_intake`, `p1_site_analytics`, `p1_submission_reference`.
2. Secrets (Supabase dashboard -> Edge Functions -> Secrets, or `supabase secrets set`; see `.env.example`): `H2H_RESEND_API_KEY`, `H2H_TOUR_SHARED_SECRET` (32+ characters, used between `website-inquiry` and `tour-request-mailer`), optional `H2H_FROM_EMAIL` / `H2H_STAFF_NOTIFY_EMAIL`.
3. Deploy the functions:
   - `supabase functions deploy website-inquiry` (JWT verification on; the browser sends the public anon key)
   - `supabase functions deploy site-event` (JWT verification on)
   - `supabase functions deploy tour-request-mailer --no-verify-jwt` (authenticates with `H2H_TOUR_SHARED_SECRET`)

There is **no** Netlify webhook. `website-inquiry` calls `tour-request-mailer` directly for tour requests.

## How data flows

- Every form (enrollment, contact, registration, information request, tour) posts JSON from `assets/inquiry.js` to the `website-inquiry` Edge Function. It calls the service-role-only SQL functions `submit_website_inquiry_p1` / `submit_child_registration_p1`, which write to `website_private.inquiries` / `website_private.child_registrations` (RLS on, no public policies, rate limits per source and email) and return a **reference** (`H2H-YYYYMMDD-XXXXXXXX`) that is stored in the row's `reference` column.
- **Duplicates:** an identical submission (same email, kind, contact details and content) within 10 minutes returns the existing reference and sends nothing new. A different kind, child or message from the same parent is always stored and emailed. Resend idempotency keys are derived from the reference, so one stored submission is never emailed twice and separate submissions are never suppressed.
- **Staff alerts** go to `tohearts25@gmail.com` and contain the inquiry type, language, time and reference; registration and information alerts contain no contact details, child names or form text. Staff match an alert to its record by searching the `reference` column in Supabase. Tour alerts additionally include the family's contact details so staff can call them. Records created before 1.1.0-P1 have no reference.
- **Family emails:** English uses `registration-welcome.ts` / `interest-message.ts` (with `welcome-hearts.png`); es, fr, ar and sw use `brand-mail.ts`. Tour requests are forwarded to `tour-request-mailer`, which sends the staff alert and the family email.
- **Analytics:** `assets/analytics.js` posts cookie-less events to `site-event`; success events are recorded server-side by `website-inquiry`. Only daily aggregate counters are stored in `website_private.analytics_daily`.

## Security notes

- No secrets are committed. The Supabase **anon (publishable)** key is supplied at build time as `H2H_PUBLIC_ANON_KEY`; it is public by design (it ships to every visitor) and is protected by RLS and service-role-only functions. An earlier commit in history (the initial import) contains this same public anon key; that is expected and not a credential leak. Never commit the `service_role` key, Resend keys or `H2H_TOUR_SHARED_SECRET`.
- Netlify Forms is disabled and unused.
- Never commit `.env` files, exported registrations, CSVs or database dumps (see `.gitignore`).
- `public/_headers` sets a strict CSP; update `connect-src` if the Supabase project changes.

## Version 1.2.0 — Three independent workflows

| Workflow | Page | Backend | Confirmation |
|---|---|---|---|
| Register a child | `/register/` (multi-step enrollment application, 5 languages) | `submit-enrollment` Edge Function (form `1.2.0-E1`) | `/registration-received/` |
| Schedule a tour | `/tour/` | `website-inquiry` (kind `tour`) | tour confirmation |
| Request more information | `/request-information/` | `website-inquiry` (kind `information`) | `/information-received/` |

None requires another. Enrollment details: `docs/ENROLLMENT_FIELD_MAPPING.md` (regenerate with `node tools/gen-field-mapping.mjs`), open items: `docs/MANAGEMENT_DECISIONS.md`.

**Enrollment pipeline.** The schema (`enrollment/build-schema.mjs` → `schema.json`) drives the form, the server validation and the PDF. After editing anything in `enrollment/` run `node tools/sync-enrollment-function.mjs` and redeploy `submit-enrollment`. Answers live only in browser memory (no web storage, 15-minute idle clear). On submit the server validates, encrypts (AES-256-GCM, key in the `H2H_APP_DATA_KEY` secret), saves, then builds the PDF (fonts fetched from `https://hearts25.com/assets/fonts/`), stores an encrypted copy privately, and emails the unencrypted PDF to the Director (names/health details only in the attachment, never the body). Each step has a status and is retried; admin retry uses `H2H_ADMIN_SECRET`.

**Tests.** `node enrollment/core.test.mjs`, `node enrollment/check-i18n.mjs`, `node enrollment/test/e2e-function.mjs`, `python3 enrollment/test/e2e-ui.py`, `python3 enrollment/test/e2e-info.py`, `python3 tools/check-v120.py`. Synthetic PDF: `node enrollment/test/make-sample.mjs`. Synthetic data only.
